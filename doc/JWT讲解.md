# JWT（JSON Web Token）讲解

一句话：**JWT 是一种轻量、自包含的令牌格式，用 JSON 结构编码，一般用签名保证完整性，常用于 OAuth2 / OIDC 的 ID Token，也可以做业务的 access_token。**

> 
> ⚠️ 重点：JWT 只是**令牌格式**，不是 OAuth2 本身。OIDC 的 `id_token` 规定必须是 JWT；access_token 可以是 JWT，也可以是不透明字符串（引用令牌）。

## 一、JWT 结构

格式：`Header.Payload.Signature`，三段用**点 `.`**分割，Base64URL 编码（不是普通 Base64）

### 1. Header 头部

描述：**加密算法 + token 类型**

```
{
  "alg": "HS256", // 签名算法：HS256对称 / RS256非对称（OIDC推荐RS256）
  "typ": "JWT"
}
```

- HS256：对称加密，**同一个密钥用来签名 + 验签**
- RS256：非对称（RSA），**私钥签名，公钥验签**（OIDC 首选，安全）

### 2. Payload 载荷（核心数据）

存放声明 `claims`，分三类：**注册声明、公共声明、私有声明**

> 
> ⚠️ **Payload 只是 Base64 编码，不是加密！任何人拿到 JWT 都可以解码看到里面内容，不要放密码等敏感数据！**

**标准注册声明（OIDC id_token 常用）**

- `iss` Issuer：签发者（授权服务器地址）
- `sub` Subject：用户唯一标识（主体）
- `aud` Audience：受众，这个 token 是给谁用的（你的 client_id）
- `exp` Expiration Time：过期时间戳（Unix 时间），**必须校验**
- `iat` Issued At：签发时间
- `nbf` Not Before：在此时间前不能使用
- `nonce`：OIDC 专用，就是前面讲的 nonce，用来防 id_token 重放

**自定义私有声明**：业务自己加，比如 `role:admin`

### 3. Signature 签名

公式：

```
Signature = HMAC-SHA256(
  base64url(Header) + "." + base64url(Payload),
  密钥
)
```

作用：**保证 Header + Payload 没有被篡改**。
验签逻辑：资源服务器拿到 JWT 后，用密钥 / 公钥重新计算签名，对比 token 里的签名。

- 一致：内容没被改
- 不一致：被篡改，直接丢弃

## 二、JWT 完整校验清单（面试高频！）

拿到 JWT（id_token）后端必须逐项校验：

1. ✅ 校验签名（最重要，保证没被篡改）
2. ✅ 校验 `exp` 过期时间，不能过期
3. ✅ 校验 `iss` 签发者，必须是可信授权服务器
4. ✅ 校验 `aud` 受众，必须等于当前应用 client_id（防止 token 发给别的应用）
5. ✅ 校验 `nbf`（如果存在），当前时间不能早于 nbf
6. ✅ OIDC 场景：校验 `nonce` 和会话保存的 nonce 一致

> 
> 少任何一项，就会存在安全漏洞！

## 三、JWT 的两种使用场景

1. **OIDC 的 id_token（固定 JWT）**
用来做身份认证，告诉应用「这个用户是谁」，包含用户身份 claims。
2. **access_token（可选 JWT）**
   - JWT access_token：自包含，资源服务器不需要远程调用授权服务器，**本地验签即可**（本地校验）
   - 不透明 access_token（随机字符串）：资源服务器需要调用授权服务器 `/introspect` 内省接口，远程校验 token 信息

> 
> JWT access_token 里面一般会带上 `scope`，资源服务器校验 scope 判断权限。

## 四、JWT 的优缺点

✅ 优点

1. **自包含**：信息都在 token 里，不用查数据库存会话（无状态）
2. 格式标准化，跨语言
3. 适合分布式、微服务，资源服务器本地验签

❌ 缺点

1. **不能撤销**：JWT 一旦签发，在 exp 过期前，默认无法作废（无状态）。想要撤销要额外方案：黑名单、短有效期。
2. 体积大：携带很多 claims，每次请求都在 header 传输，token 越长 http 开销越大
3. **仅编码不加密**：payload 明文可读，不能存敏感信息

## 五、高频误区

❌ JWT 是加密的，别人看不到内容

> 
> 错！只是 Base64URL 编码，直接解码就能看载荷；签名只是防篡改，不是加密。要加密用 JWE。

❌ 签名可以防止别人读取 JWT 内容

> 
> 不能，签名只防篡改，不防读取。

❌ HS256 适合分布式 OIDC 场景

> 
> 不推荐。HS256 是对称密钥，验签方也要持有密钥，密钥分发风险大；OIDC 推荐 RS256，授权服务器用私钥签名，对外暴露公钥（JWKS）给业务方验签。

## 六、面试一句话总结

JWT 是自包含的签名令牌，三段式（Header.Payload.Signature）；Payload 存放声明，Base64 编码不加密；签名保证内容未篡改；OIDC 的 id_token 强制 JWT，access_token 可选 JWT；使用时后端必须校验签名、iss、aud、exp 等字段；无状态，但默认无法撤销。

## 关联串起来

- OIDC 授权成功返回 id_token（JWT）+ access_token
- id_token 里包含 nonce，用来校验本次会话
- access_token 携带 scope，访问资源 API 鉴权


# 对称密钥 vs 非对称密钥（结合 JWT/OIDC 场景来讲，面试友好）

## 一句话概括

- **对称加密（Symmetric）：同一个密钥，加密和验签都用它。一把锁，开锁和上锁是同一把钥匙。**
- **非对称加密（Asymmetric）：一对密钥（私钥 + 公钥）。私钥自己保管用来签名；公钥公开出去，所有人用来验签。**

> 
> 注意：JWT 里我们说的是**签名**，不是数据加密，原理类似。
> 
> 
> - HS256：对称签名算法
> - RS256 / ES256：非对称签名算法

## 1. 对称密钥（HS256 举例）

### 流程

1. 授权服务器有一个**密钥 secret**
2. 授权服务器用这个 secret 对 JWT 做签名，生成 JWT
3. 你的后端（资源服务器）**必须保存完全相同的 secret**，使用它来校验 JWT 签名

✅ 优点

- 算法简单，计算速度快
- 实现简单

❌ 缺点

- **密钥分发困难，风险高**：签名方和验签方都要持有同一个密钥。任何一方泄露，整个体系就崩了。
- 多服务场景很难管理：如果有几十上百个业务系统都要验签 JWT，每个系统都要存这个密钥，泄露面变大。

👉 **适用场景**：单服务内部，只有你自己系统签发 + 校验 JWT，只有一个服务持有密钥。
👉 **OIDC 不推荐用 HS256**：因为 OIDC 有很多客户端，不能把核心密钥分发出去。

## 2. 非对称密钥（RSA RS256 举例）

一对密钥：**私钥 private key、公钥 public key**

> 
> ⚠️ 私钥和公钥成对生成，不能随便造。
> 
> 
> - **私钥：保密！只留在授权服务器，用来签名 JWT。绝不对外暴露。**
> - **公钥：可以公开！任何人都可以拿到公钥，用来验证签名。公钥不能用来签名。**

### 流程（OIDC 标准做法）

1. 授权服务器生成 RSA 密钥对：私钥、公钥
2. 授权服务器**私钥签名**JWT（id_token）
3. 公钥放到 JWKS 端点（`/.well-known/jwks.json`）公开给所有客户端
4. 业务后端拿到 JWT 后，去 JWKS 获取公钥，**用公钥验签**

✅ 优点

- 安全：**私钥不外泄**，只授权服务器持有。公钥随便公开。就算公钥被别人拿到，也不能伪造 JWT。
- 适合分布式、多客户端场景（OIDC、SSO 首选）

❌ 缺点

- 计算开销更大，比 HS256 慢一点
- 实现稍微复杂一点，还要维护 JWKS、密钥轮换

## 3. 核心对比表

表格

| 对比项 | 对称密钥 HS256 | 非对称密钥 RS256 |
| --- | --- | --- |
| 密钥数量 | **单个密钥**，双方共用 | 一对密钥：私钥、公钥 |
| 签名使用的密钥 | 共享密钥 | 私钥（保密） |
| 验签使用的密钥 | 共享密钥 | 公钥（公开） |
| 密钥能否对外分发 | ❌ 绝对不能泄露 | ✅ 公钥可以公开 |
| 泄露后果 | 密钥一旦泄露，攻击者可以伪造 JWT | 公钥泄露无害；只有私钥泄露才危险 |
| 性能 | 快 | 较慢 |
| OIDC 推荐 | 不推荐 | ✅ 推荐标准方案 |

## 4. 高频面试坑点

❌ 误区 1：非对称加密，公钥加密、私钥解密 → 套用到 JWT 签名

> 
> JWT 签名场景逻辑反过来：**私钥签名，公钥验签**。
> 加密场景：公钥加密，私钥解密。不要搞混两个场景！

❌ 误区 2：公钥可以用来生成签名

> 
> 不行。公钥只能验证签名，不能生成合法签名。只有私钥能签名。

❌ 误区 3：对称密钥 = 不安全

> 
> 不是绝对不安全，**是密钥分发场景不安全**。单应用内部自己玩 HS256 没问题；多客户端 OIDC 场景风险巨大。

## 5. 结合之前 OIDC 串起来

OIDC 授权服务器使用 RS256：

1. 授权服务器用私钥签名 id_token（JWT）
2. 业务应用拿到 id_token，去 JWKS 拿公钥
3. 使用公钥校验签名，确认 JWT 没有被篡改
4. 再校验 exp、iss、aud、nonce 等 claims

## 一句话背诵版

对称加密：**一钥两用，签名验签同一个密钥，分发难，适合单机**；
非对称加密：**公私钥成对，私钥签名保密，公钥验签公开，适合 OIDC 分布式 SSO**。

# JWT 公钥验签到底是什么（用大白话 + 原理讲）

先回顾 JWT 结构：`Header.Payload.Signature`

> 
> Signature = 授权服务器用**私钥**计算出来的签名值。

**验签：业务后端拿到 JWT，使用【公钥】重新计算一遍签名，对比算出来的结果和 JWT 自带的 Signature 是否一致。**
一致 = 证明两件事：

1. 这个 JWT 一定是**持有对应私钥的授权服务器签发**，不是别人伪造的
2. Header 和 Payload 在传输途中**没有被篡改**

> 
> ⚠️ 公钥**不能生成签名**，只能校验签名真假。私钥才能生成签名。

## 一、完整拆解 RS256 签名过程（授权服务器）

1. 把 Header、Payload 分别做 Base64URL 编码，拼接成字符串：`base64Url(header).base64Url(payload)`
2. 授权服务器拿出自己的 RSA**私钥**，对上面这个字符串做签名运算，得到一串二进制签名，再 Base64URL 编码 → 就是 JWT 第三段 Signature
3. 拼接三段，返回给客户端：`Header.Payload.Signature`

> 
> 私钥只有授权服务器手里，不会对外放出。

## 二、业务后端「验签」的步骤

业务后端拿到 JWT：`H.P.S`

1. 拆分三段：H、P、S（S 是传过来的原始签名）
2. 从 JWKS（`/.well-known/jwks.json`）拉取授权服务器公开的公钥
3. 把 H、P 同样 Base64URL 编码拼接，使用**公钥**执行验签算法
> 
> 算法内部：用公钥 + 原始 H+P，校验传入的 S 是不是私钥生成的合法签名
4. 算法返回结果：
   - ✅ 校验通过：H 和 P 内容没改动，确实是授权服务器签发
   - ❌ 校验失败：直接丢弃这个 JWT，拒绝登录

## 三、举个篡改例子理解为什么验签能防篡改

假设攻击者拿到 JWT：
原始 payload：`{"sub":"user100","role":"user"}`
攻击者修改 payload，改成：`{"sub":"user100","role":"admin"}`
然后自己 Base64 编码，想伪造一个新的 Signature。

但是！**攻击者没有授权服务器的私钥**，无法计算出能被公钥验证通过的签名。
业务后端拿公钥一验签 → 校验不通过，请求拦截。

> 
> 哪怕攻击者修改一个字符，重新算出来的签名就对不上。

## 四、重点区分两个容易混淆概念

1. **签名（私钥操作）**：生成凭证，证明这是我发的。授权服务器做。
2. **验签（公钥操作）**：验证凭证真假，确认没被篡改。业务后端做。

> 
> 这不是「解密」！！！
> ❗ 非常关键：RS256 JWT 签名场景，**没有解密动作**。
> Payload 一直是 Base64URL 编码，任何人都可以解码查看内容。
> 验签只是校验签名合法性，不会解密。
> 
> 
> 加密场景（JWE）才是：公钥加密，私钥解密。JWT（JWS）只是签名，不是加密。

## 五、JWKS 在里面扮演的角色

JWKS 是授权服务器暴露的公钥集合（JSON），里面包含公钥，还有 `kid`（Key ID）。

- JWT header 里面有 `kid`，代表这个 JWT 是用哪一把密钥签名的
- 后端拿到 JWT，读取 header 的 kid，去 JWKS 找到对应公钥，再验签

> 
> 好处：支持**密钥轮换**，授权服务器定期更换密钥对，业务后端不用改配置，自动拉取最新公钥。

## 六、面试一句话总结验签

验签就是：业务后端拿到 JWT，使用从 JWKS 获取的公钥，重新校验 Header+Payload 的签名，确认令牌是授权服务器私钥签发，并且中途没有被篡改。**验签≠解密。**

## 补充：HS256（对称）的验签对比

HS256 没有公私钥：
授权服务器用共享密钥算出签名；业务后端**用同一个共享密钥**重新计算签名，对比和 JWT 里的签名是否一致。

> 
> 共用同一个密钥，这就是对称。
