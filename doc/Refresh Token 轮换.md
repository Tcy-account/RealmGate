# Refresh Token 轮换（Refresh Token Rotation）

一句话：**Refresh Token 轮换，就是每次用 refresh_token 去刷新 access_token 的时候，授权服务器不再返回原来那枚 refresh_token，而是返回一枚全新的 refresh_token；旧的 refresh_token 会立刻被吊销作废。**

> 
> 注意：这不是默认行为，是可开启的特性，需要授权服务器（Keycloak、Auth0 等）配置开启。
> 原生 OAuth2 规范没有强制轮换 refresh_token，默认是**同一个 refresh_token 可以反复多次用来刷新令牌**。

## 1. 不开启轮换（默认传统模式）

- 拿到 `RT1`
- 每次刷新 access_token，一直复用 `RT1`，反复使用
- 直到 RT 过期、被手动 revocation 吊销
- 风险：一旦 `RT1` 被盗，攻击者可以无限持续刷新新 access_token，直到这个 RT 到期。

## 2. 开启 Refresh Token Rotation 后的流程

1. 客户端拿着旧 `refresh_token: RT1`，调用 `/token` 刷新令牌
2. OP 校验 RT1 有效，生成新的 `access_token`，**同时生成一枚全新 RT2 返回**
3. OP **立刻吊销旧的 RT1**，RT1 之后再也不能使用
4. 客户端后续刷新，必须使用新返回的 RT2
5. 下一次刷新：提交 RT2 → 返回 RT3，RT2 作废，以此不断轮换

请求示例（刷新接口）

```
POST /token
grant_type=refresh_token
&refresh_token=RT1
&client_id=xxx
&client_secret=xxx
```

返回：

```
{
  "access_token": "AT-new",
  "token_type": "Bearer",
  "expires_in": 300,
  "refresh_token": "RT2", // 新的refresh token
  "id_token": "xxx"
}
```

## 3. 核心解决的安全问题

**降低 refresh_token 泄露带来的风险**
refresh_token 是长期令牌，如果被盗：

- 不开启轮换：攻击者拿到 RT，可以一直刷新，直到 RT 过期；
- 开启轮换：只要正常用户使用一次刷新，旧 RT 直接作废。攻击者手里偷来的旧 RT 直接失效。

> 
> 举例子：
> 黑客窃取了 RT1，还没来得及使用；
> 正常用户发起一次 token 刷新，提交 RT1，服务器返回 RT2，同时吊销 RT1；
> 黑客手里的 RT1 直接废掉，无法再用。

## 4. 配套：滑动窗口（Concurrent Session / 并发保护，Keycloak 这类常用）

有一个边界问题：网络延迟导致**重复请求**。
比如客户端网络抖动，重复发了两次同样的刷新请求（都带 RT1）：

- 第 1 个请求：成功，返回 RT2，吊销 RT1
- 第 2 个请求到达 OP 时，RT1 已经被吊销，如果直接返回失败，客户端会刷新失败。

解决方案：**短暂的滑动窗口**
OP 在吊销旧 RT 之后，保留一小段宽限时间（几十秒）。
在窗口内，同一个 RT 的第二次请求，仍然允许返回新 RT；窗口过后，旧 RT 彻底拒绝。

> 
> 目的：应对网络重试，避免偶发刷新失败。

⚠️ 安全权衡：窗口期间，如果黑客拿到旧 RT，也能在窗口内换取一次新 token。窗口时间不能设置太长。

## 5. 什么时候会丢失 refresh_token？

客户端**必须保存每次刷新返回的新 refresh_token**，覆盖本地存储的旧 RT。

> 
> 严重 bug：刷新拿到新 RT，但客户端没有更新本地存储，下次继续提交旧 RT → 请求失败。

## 6. 面试重点：区分两个容易混淆概念

### Refresh Token Rotation（RT 轮换）

每次刷新，换新 RT，旧 RT 作废。**用来降低令牌泄露风险。**

### Refresh Token 滑动过期（Sliding Expiration）

每次刷新成功，**延长当前这枚 refresh_token 的过期时间，RT 本身不变**。

- RT 有效期不断往后推迟；
- 长时间活跃的用户，可以一直保持登录；长时间不操作，RT 过期下线。

> 
> 👉 轮换：换令牌；滑动过期：延长令牌有效期，令牌不变。两者可以同时开启。

## 7. 优缺点

✅ 优点

1. 提升安全性，RT 泄露之后生命周期变短，攻击窗口缩小
2. 适合前端 SPA、移动端这类令牌容易泄露的客户端（公共客户端）

❌ 缺点

1. 客户端开发复杂度提升：每次刷新**必须持久化保存新 RT**
2. 网络重试场景，需要 OP 滑动窗口兼容
3. 如果客户端丢失最新 RT，刷新直接失败，需要用户重新登录

## 8. 适用场景

- ✅ 移动端 APP、原生客户端、SPA 公共客户端（没有安全后端存储，RT 容易泄露，强烈推荐开轮换）
- ✅ 高安全业务系统
- ❌ 后端机密客户端（服务端服务之间调用，RT 存在安全数据库，泄露风险低，一般不开）

## 9. 常见坑

❌ 误区 1：轮换会延长 RT 有效期

> 
> 不是。轮换是**生成全新 token**；滑动过期才是延长有效期。两个独立配置。

❌ 误区 2：开启轮换后，RT 永久不会过期

> 
> 新 RT 依然有最大生命周期，到最大生命周期，就算不断轮换，也会强制失效，要求用户重新登录。

❌ 误区 3：旧 RT 可以继续多次使用

> 
> 一旦刷新成功，旧 RT 立即吊销（除滑动窗口宽限期），不能再次使用。

## 一句话背诵面试版

Refresh Token 轮换：每次用 refresh_token 刷新 access_token 时，OP 返回全新 refresh_token，旧 refresh_token 立即吊销；目的是缩小 refresh_token 被盗后的攻击窗口；和滑动过期不同，轮换是换新令牌，滑动过期是延长原有令牌有效期；客户端必须保存每次返回的新 RT；网络重试场景需要授权服务器开启滑动窗口兼容。

## 整体串联

1. 用户登录拿到 AT、RT1
2. AT 过期，客户端拿 RT1 刷新
3. OP 校验 RT1 有效，生成新 AT、**新 RT2**，吊销 RT1
4. 客户端本地保存 RT2，后续刷新使用 RT2
5. 如果 RT1 被黑客窃取，只要用户完成一次刷新，黑客手里的 RT1 直接失效
